# The decompilation knowledge base

Field notes on how binaries were actually decompiled and reconstructed, **written by agents for the next
agent** and reviewed through pull requests. Each note records what one project learned the hard way: exact
versions, the route and why, what the program or engine really does, how it was verified, and the
**gotchas** (symptom -> cause -> fix).

- [`INDEX.md`](INDEX.md) lists every note (`index.json` is the same data for tools; both generated by
  `ud kb index`).
- `<title>/<note>.md`: one decompiled title per folder (kind `title`).
- `<family>/<note>.md`: topics about a family or a tool (kind `topic`), e.g. `tooling/`.
- Per-family routes and tools live with the skills:
  [`../skills/decompile-any-binary/references/engines/`](../skills/decompile-any-binary/references/engines/).

## Search before you start
```bash
ud kb search "<title>"                   # in a clone, or anywhere (it syncs this folder from GitHub)
ud kb search pyghidra --family tooling
ud kb show tooling/pyghidra-mcp-setup.md
```

## Write it up at the end (or when you get stuck)
```bash
ud kb new --subject "<title>" --title "<what you reconstructed>" --from-scan data/<binary> --agent "<agent (model)>"
ud kb check knowledge/<folder>/<note>.md
ud kb pr knowledge/<folder>/<note>.md        # dry run; --yes only after your human agrees
```
Rules (full list in [`../CONTRIBUTING.md`](../CONTRIBUTING.md)): no binaries, no assets, **no decompiled
code**, no address tables large enough to rebuild code, honest status and verification, the agent and model
named. `ud kb check` rejects code blocks over 40 lines, decompiler-looking output (`undefined4`, `uVar1`,
`param_1`, `FUN_00401000`...) and more than 40 distinct addresses.

## What makes a good note
- **Versions.** "Ghidra 12.1.4, pyghidra-mcp 0.2.7, GOG build 1.02" beats "latest".
- **Gotchas with causes.** "Enemies desync after 30 s because the original calls the RNG once more per dead
  enemy" is reusable; "AI was buggy" isn't.
- **The oracle.** How you knew it matched, so the next agent can re-check after a different build.
- **Your own words.** Describe logic, name algorithms and structures; link to your private work only if it's
  allowed to be seen (it usually isn't).
